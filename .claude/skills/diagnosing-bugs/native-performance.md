# Native performance diagnosis

Use this branch of [diagnosing-bugs](SKILL.md) for slow native startup, rendering or camera movement. Keep the accepted diagnostic allowance and save custody throughout.

1. **Capture the ordinary baseline.** Observe the reported failing process before replacing it with a helper launch. While it is alive, retain its executable identity, actual arguments and working directory, selected save/artwork, relevant graphics environment settings, adapter/backend, window size and focus state. Record unset settings explicitly and unavailable observations as unknown. Use an allowlist for environment capture. Measure the reported symptom; a kernel warning or successful allocation alone does not establish usable rendering. If the process has already exited, retain the owner's exact command and mark uncaptured conditions unknown until a bounded reproduction supplies them.

2. **Freeze the comparison.** Finish owned builds before timed runs and keep the executable fixed across each comparison. Instrumented source copies use the existing [isolated build procedure](../../../docs/agents/native-verification.md#build-an-instrumented-source-copy). Record when observation itself reads files, hashes the executable, captures a frame or adds logging: those actions can change startup timing.

3. **Expose launch differences.** Compare the ordinary baseline with the existing helper's `run.json`. A helper launch is a distinct experimental condition even when executable bytes match: it stages executable/save copies, changes cwd and XDG directories, redirects standard streams, verifies the running executable and may request a screenshot or initial view. The manifest's inherited settings describe the helper's environment; they cannot recover an exited owner's process. Keep necessary save isolation and state its difference. Change one relevant condition per comparison; an unmatched healthy run establishes only that run's result.

4. **Measure valid foreground intervals.** Follow [foreground performance measurements](../../../docs/agents/native-verification.md#foreground-performance-measurements). Preserve wall-clock limits while recording usable foreground samples or duration. Compare the same activity and scene. Use targeted timings to separate main-thread work, upload writes and GPU completion before expanding a launch matrix. GPU completions measure progress, not physical display timestamps.

5. **Test the cause, then the original command.** Where a diagnostic policy switch permits it, use one executable for original → changed → original comparisons; retain the failing control and reversal. If that comparison is unavailable, state the limitation. After implementing the repair, rerun the ordinary launch command with its relevant conditions restored, including removal of diagnostic instrumentation. Keep record custody explicit and distinguish verified rendering progress from owner gameplay acceptance. Retain the commands, measured results and evidence locations in the existing issue or PR.

## Owner-run measurement launch

Use this when the owner's display is the oracle and the owner starts the app from a terminal. It supplies no agent desktop access. The launch counts against the issue's ceiling whether its result is accepted, rejected or inconclusive, so steps 1 to 6 are complete before it starts.

1. **Commit the instrument to a diagnostic branch and review it there.** Format, strict Clippy, the affected library tests and, before the commit, the index guard are its recorded checks. Where a condition depends on window focus, the instrument records focus itself: the table logs it only at `debug`. The full gate applies only once the branch is proposed for `main`; run from a worktree that shares the owner's target, it replaces the normal executable.
2. **Build it once, after review,** with the [isolated build helper](../../../docs/agents/native-verification.md#build-an-instrumented-source-copy). Its fresh target recompiles every dependency: about twelve minutes on the owner's machine on 2026-11-12. Record the commit, the executable's SHA-256 and the unchanged SHA-256 of the normal executable.
3. **Stage private inputs in a fresh folder outside the checkout.** Copy the save to open, check the copy with the headless driver's [`--inspect`](../../../README.md#direct-diagnostic-launch), and leave the owner's attempt and Continue reference untouched. State how this launch differs from the owner's normal one.
4. **Write a thin launcher there** so the owner pastes one command. It changes to the staging folder, fixes the save, keeps `info` logging in the [`RUST_LOG` form the pacing counter uses](../../../docs/agents/native-verification.md#foreground-performance-measurements), and starts the app under the recorder's [resource measurements](../../../docs/agents/measured-and-baseline-checks.md#resource-measurements). From that folder the recorder fingerprints no checkout; its `check.log` is the app's log, and its samples show whether something else was loading the machine. Take an app-closed reading first when the measurement needs a baseline. Before the app starts, the launcher also saves three readings the app's log lacks into files in the staging folder:
   - `xrandr --current`: the screen size Xwayland draws for.
   - `gsettings get org.gnome.mutter experimental-features`: whether the desktop scales Xwayland's output. With the display's own size, these two let the record infer how far the desktop shrinks the window.
   - `nvidia-smi -q -d POWER,TEMPERATURE`: the card's power limit, and the temperature at which it slows itself.
5. **Exercise the executable through that launcher without the owner,** where the [agent seat](../../../README.md#agent-seat) can run it with the instrument on: add the seat's options to the launcher's command, then read what it recorded. The seat's evidence limits there name what only the owner's launch exercises; carry them into the handoff.
6. **Hand over before the launch.** Give the owner the whole route, as [capture preparation](../../../docs/agents/native-verification.md#capture-preparation) sets out, in the [private checklist](../../../docs/agents/native-verification.md#prepare-a-compact-native-handoff), and post the [public current handoff](../../../docs/agents/issue-tracker.md#current-handoff) after its [preflight](../../../docs/agents/native-verification.md#public-handoff-preflight). A measurement adds two things to the route: every condition is held long enough to measure, and the stretch that runs with part of the instrument off comes last.
7. **Record the conditions after it.** The table's log states the adapter and driver, and the window's physical size and scale factor. [`resource-summary`](../../../docs/agents/measured-and-baseline-checks.md#resource-measurements) shows where host CPU rose while the launched command's stayed level. Set its windows on the instrument's clock with `--origin-unix-ms`, and name each measured stretch such a rise overlapped. Ask the owner about screen sharing, recording and other heavy programs.
8. **Publish the result.** Post the evidence record, bring the current handoff up to date, and keep the launch's files as [final evidence retention](../../../docs/agents/native-verification.md#retain-final-verification-evidence) describes. The record keeps the owner's words apart from the measurements and says what the timers cannot show. The diagnostic branch stays unmerged: pushing it so the record's commit can be inspected, or proposing any of it for `main`, is the owner's decision.
