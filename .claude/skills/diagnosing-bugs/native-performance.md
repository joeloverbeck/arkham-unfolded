# Native performance diagnosis

Use this branch of [diagnosing-bugs](SKILL.md) for slow native startup, rendering or camera movement. Keep the accepted diagnostic allowance and save custody throughout.

1. **Capture the ordinary baseline.** Observe the reported failing process before replacing it with a helper launch. While it is alive, retain its executable identity, actual arguments and working directory, selected save/artwork, relevant graphics environment settings, adapter/backend, window size and focus state. Record unset settings explicitly and unavailable observations as unknown. Use an allowlist for environment capture. Measure the reported symptom; a kernel warning or successful allocation alone does not establish usable rendering. If the process has already exited, retain the owner's exact command and mark uncaptured conditions unknown until a bounded reproduction supplies them.

2. **Freeze the comparison.** Finish owned builds before timed runs and keep the executable fixed across each comparison. Instrumented source copies use the existing [isolated build procedure](../../../docs/experiments/jacqueline-curse.md#build-an-instrumented-source-copy). Record when observation itself reads files, hashes the executable, captures a frame or adds logging: those actions can change startup timing.

3. **Expose launch differences.** Compare the ordinary baseline with the existing helper's `run.json`. A helper launch is a distinct experimental condition even when executable bytes match: it stages executable/save copies, changes cwd and XDG directories, redirects standard streams, verifies the running executable and may request a screenshot or initial view. The manifest's inherited settings describe the helper's environment; they cannot recover an exited owner's process. Keep necessary save isolation and state its difference. Change one relevant condition per comparison; an unmatched healthy run establishes only that run's result.

4. **Measure valid foreground intervals.** Follow [foreground performance measurements](../../../docs/experiments/jacqueline-curse.md#foreground-performance-measurements). Preserve wall-clock limits while recording usable foreground samples or duration. Compare the same activity and scene. Use targeted timings to separate main-thread work, upload writes and GPU completion before expanding a launch matrix. GPU completions measure progress, not physical display timestamps.

5. **Test the cause, then the original command.** Where a diagnostic policy switch permits it, use one executable for original → changed → original comparisons; retain the failing control and reversal. If that comparison is unavailable, state the limitation. After implementing the repair, rerun the ordinary launch command with its relevant conditions restored, including removal of diagnostic instrumentation. Keep record custody explicit and distinguish verified rendering progress from owner gameplay acceptance. Retain the commands, measured results and evidence locations in the existing issue or PR.
