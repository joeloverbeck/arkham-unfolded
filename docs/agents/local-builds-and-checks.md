# Local builds and checks

The built application runs offline. A clean clone needs no artwork or credentials for headless engineering checks. Complete prepared artwork and successful decoding are required for 3D play. Run `scripts/check` before publication; it owns the phase order. Before its phases, `scripts/tools target-prune --older-than 1d --delete` removes this repository's superseded builds and incremental caches unused for a day from the owner's Cargo target ([one target for several checkouts](measured-and-baseline-checks.md#one-target-for-several-checkouts)); only an interrupt there stops the check. Its phases cover full-workspace formatting, one shared revision across the manifests, tracked-file hygiene, the Rust tool tests, a Bevy-free build, strict Clippy, the rules, continuity and tabletop tests, and the renderer patch's pin. The application, renderer patch and tools use immutable Git revisions from `unfolded-tabletop`. `scripts/check-shared-pins` fails unless every declaration of that repository in `Cargo.toml` and `tools/Cargo.toml` names the same revision, listing each revision with its declarations; it matches the repository's URL in any letter case, and through string escapes in a line it can read, and refuses a declaration of it that is not a one-line inline table naming a `rev`, a line spelling the URL that it cannot read, a table header naming it, or a manifest with none. It does not decode escapes in keys, or find an escaped URL on a line it cannot read. It reads the manifests without Cargo, so a partial update fails there even before the lockfile records it. `scripts/check-renderer` verifies through locked Cargo metadata that the renderer resolves to that exact package. The patch's Vulkan regression tests, like the shared mechanisms' behavioural tests, run in `unfolded-tabletop`'s own check; Arkham's tests hold its adapters. The Bevy-free phase, `scripts/check-bevy-free`, checks the library, `arkham-driver` and `arkham-assets` without the `tabletop` feature, so Bevy use in rules, saves or the headless driver that is not gated behind that feature fails it, as [ADR 0006](../adr/0006-keep-bevy-and-keep-its-slice-narrow.md) requires. Focused checks support iteration; the final candidate needs this complete path. `scripts/check-format` uses `cargo fmt --all -- --check`, including the tools workspace member. Rustup uses the compiler and components in `rust-toolchain.toml`. The Ubuntu PR workflow runs the same phase launchers as named steps without a display or private assets, with formatting before builds; the portal transport tests start a private `dbus-daemon`. CI compiles its small Rust toolchain-preparation entry point and the shared-revision check directly with `rustc` before restoring Cargo's cache; the full tools package builds afterward.

On Linux x86_64 and aarch64, the file-replacement lock test uses `ptrace` to observe its own driver child. The test environment must permit this child tracing. If a restricted agent or container sandbox denies it with `Operation not permitted`, rerun the unchanged check in an authorized environment that permits child tracing. Successful verification requires the tracing test to execute and pass.

Local development defaults to two Cargo jobs. Development and test builds keep file-and-line backtraces for workspace code and omit dependency debug data, reducing the memory and disk load of linking the tabletop test suite. For full variable and dependency debugging, opt in with `scripts/dev cargo build --locked --features tabletop --bin arkham-tabletop --profile debug-full`; its executable is `target/debug-full/arkham-tabletop`.

`scripts/check` runs its phases in a transient user systemd scope: 12 GiB memory pressure threshold, 16 GiB hard memory limit, 1 GiB swap limit, six CPU equivalents and CPU weight 20. Use `scripts/dev COMMAND [ARG...]` for other local builds and individual checks, for example:

```sh
scripts/dev cargo build --locked --features tabletop --bin arkham-tabletop
scripts/dev scripts/check-app
```

Protected commands share a lock on this checkout's directory. A second command waits up to 30 seconds, then reports `flock: timeout while waiting to get lock` on stderr and exits with code 75 if the checkout is still busy; retry after the active build finishes. Lock diagnostics stay on stderr, preserving the command's stdout (including Cargo JSON) and exit status. A nested `scripts/dev` call in the same checkout, such as the one `scripts/check` makes, finds the outer call's checkout in `ARKHAM_DEV_CHECKOUT` and runs directly inside that scope and lock, so `scripts/dev scripts/check` also works. The marker passes to every process the outer command starts, so a background process that outlives the outer command, and with it the lock, also runs its `scripts/dev` calls unlocked; keep protected work in the foreground. Separate checkouts have separate locks, and a nested call into another checkout takes that checkout's own scope and lock. Run the built tabletop executable separately so compilation limits and the lock do not affect play.

The repository's [VS Code settings](../../.vscode/settings.json) route rust-analyzer's diagnostics and build-script/procedural-macro compilation through the same launcher, with the tabletop feature enabled. These use rust-analyzer's [command overrides](https://rust-analyzer.github.io/book/configuration#rust-analyzer.check.overrideCommand). A busy editor check can be rerun with **rust-analyzer: Run flycheck** after the full check finishes; other editors need equivalent local configuration.

The launcher requires `flock` and a running user systemd manager; a failed scope launch stops the command without an unlimited retry. CPU and memory controller delegation is a host prerequisite: verify the effective cgroup limits when setting up another host, since accepted systemd properties alone do not prove enforcement. A hard-limit failure is a failed check, never permission to retry without limits. Direct Cargo commands retain the job/debug defaults but do not get the systemd limits or checkout lock. CI continues to run the named phase launchers under its existing runner settings.

A restricted agent can be denied access to the user session bus even when the user manager is running. `Failed to connect to user scope bus via local transport: Operation not permitted` means the launcher failed before the check started. Retain the failed record, then rerun the unchanged command with authorized host access to that bus, keeping `scripts/dev` and its limits in place. Use a fresh `record-check` output directory and require a finished, successful record before treating the check as passed.

In a Git checkout, the recorder fingerprints tracked and non-ignored untracked files before and after the child runs, including dirty contents, missing files, permissions and symlink targets. The record directory itself is excluded. Changed inputs set `status` to `invalidated` and make a successful child return failure from the recorder; the original child `exit_code` is retained. Fingerprint errors produce `incomplete` evidence. Outside Git, the source fields are null. These endpoint fingerprints do not detect edit-and-revert during a run, follow external symlink contents, or cover ignored build inputs; keep the candidate stable throughout verification. Submodule entries are refused rather than silently omitted.

After a recorded check fails, `record-check` automatically prints diagnostic excerpts using `check-summary`, with a 6,000-byte combined budget for paths, recorder notices and excerpts. It preserves the child's exit status, the complete log and `run.json`; unavailable excerpts do not replace the check result. Successful checks print their retained paths and any resource-capture warning.

For a running or apparently stalled check, inspect its retained record first, then bounded diagnostic excerpts. `check-summary` limits both individual lines and total output, reports omissions, and links the unchanged full log. Its recognized compiler/test/formatting markers are navigation hints, not a success verdict; unrecognized output gets a bounded tail. If the record is still running, use its exact `pid` with compact process columns; replace `RECORDED_PID` below with that number. This avoids dumping wrapper arguments or unrelated processes:

```sh
cat /absolute/path/to/new-check-record/run.json
scripts/tools check-summary /absolute/path/to/new-check-record/check.log --max-bytes 6000
ps -p RECORDED_PID -o pid,etime,stat,comm
```

A live PID shows process presence, not check success. Use a finished `run.json` even when the tool session's terminal status was lost; losing that status alone does not justify rerunning unchanged work. If the process has gone away without a finished record, retain the result as incomplete.

To record resource measurements with a check, to compare a behavior-preserving refactor against a baseline revision, or to share one Cargo target across several checkouts, follow [measured and baseline checks](measured-and-baseline-checks.md).

## Repository helpers

Repository helpers live in the independent `arkham-tools` Cargo package. `scripts/tools --help` lists the bounded reader, Git-index guard, native verification and profiling commands, the agent seat's `seat` and `seat-wait` commands and the agent partners' `partner` command; building these helpers does not compile Bevy. The launcher isolates its build artifacts from application compilation so context reads can proceed during a build, while Cargo still rebuilds changed helper sources. Its invocation parameters leave the caller's build-directory environment available to commands such as `record-check`. The index guard rejects generated caches and recognizable non-Rust executable source/template filenames, including force-added files. Inline code, templates and invocation-only shell remain subject to review under the [implementation-language contract](../foundation/mission.md#implementation-language). See the experiment guide for [native verification](native-verification.md#developer-native-verification), external inputs, records and evidence limits.

## External inputs

The application reads a separately configured prepared asset collection. Image and font bytes are not included in Git. The [selected artwork contract](../adr/0004-require-artwork-for-3d-play.md) requires complete artwork and successful loading before 3D play, with informative refusal and recovery instead of substitutes. Absent or unsupported rules behavior must also be identified before play. The [source contract](../foundation/sources-and-verification.md#presentation-asset-preparation) requires deliberate selection, copying/conversion and verification whenever development introduces a new asset dependency. The original archive's layout and source identities belong to that preparation step.

Once required game data is imported, gameplay and saves work offline. ArkhamDB remains the deck editor; imports and update checks require network access. Personal saves, captures, and credentials remain local and outside Git.
