# Tabletop frame pacing and idle redraws

Research on 2026-10-30 supports the bounded repair in [#43](https://github.com/joeloverbeck/arkham-unfolded/issues/43). The application baseline is `9edba73e6f753fdcebd4c5eff632195ddc22ef51`; Cargo pins Bevy 0.20.0. The installed Bevy crates identify upstream commit `b3bdd75becaffe9a16677cf5bae5bd6d198f052b` in their `.cargo_vcs_info.json`. This is source-based decision support, not a measured power reduction or resolution of the previously reported severe lag. The question is how to reduce repeated rendering while preserving input, timed presentation and asynchronous completion.

## Recommended implementation after the native probe

Use Bevy's existing Winit runner with continuous updates while motion, presentation, capture or a short input-settling interval is active, plus a non-spinning 60 Hz limiter after render dispatch. When settled, select a finite low-power timeout with window/user wakeups enabled: 250 ms while focused and one second while unfocused to bound asynchronous completion delay. Relevant input should immediately enter the active interval, including pointer movement needed for hover feedback. The limiter also applies to event-triggered updates while idle, preventing an input burst from bypassing the cap. Native timing and interaction checks must establish this revised candidate's suitability.

**Superseded for active motion on 2026-11-11:** after the [cadence comparison below](#cadence-comparison-on-the-owners-display), the 60 Hz limiter no longer applies while the table is active, and FIFO presentation paces those frames. Input wakeups enter the active interval in the same update, so they are no longer capped either; the earlier input-burst protection no longer applies. The limiter now caps only dispatches made while the table remains settled, such as wakeups that bring no input. Settled timeouts are already 250 ms or one second apart.

`UpdateMode::reactive(1/60 s)` alone is insufficient: its timeout and enabled event classes are alternative reasons to update. `reactive_low_power` excludes raw device motion, which avoids waking an unfocused application merely because the mouse moves elsewhere. Neither mode is an independent GPU-present limiter. Keeping the existing FIFO VSync mode avoids introducing tearing as part of this repair. [Winit configuration](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_winit/src/winit_config.rs), [Window presentation modes](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_window/src/window.rs)

## Event delivery and timing

The runner buffers raw and converted window events before testing whether to update. `run_app_update` forwards those events into Bevy; disabling event-triggered updates delays delivery until the timed update rather than dropping input. On Linux, `about_to_wait` runs the same `should_update` gate. A `WakeUp` or `RequestRedraw` can request an OS redraw, but with all three wake flags disabled, that redraw does not independently satisfy the app-update gate before the timer. [Runner event buffering, forwarding and update gate](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_winit/src/state.rs)

The timeout uses a scheduled deadline, and missed deadlines resume from the current instant. Startup, lifecycle transitions and changes of `UpdateMode` can force additional updates. Those properties initially supported trying a 16.667 ms timeout with event-wake flags disabled, but source reasoning did not establish its actual cadence on this host. Avoid changing the chosen mode every update. Verify mouse-button presses/releases, held keys, focus loss and resize through the native path. [Runner timeout scheduling and forced updates](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_winit/src/state.rs)

### Timer-only probe and revised causal limit

The first native candidate, executable SHA-256 `0770545c054cae1f48397950df4ade307b4df62cb2916cc47e425eab1a1cfe2d`, used the 16.667 ms reactive timeout with all event-wake flags disabled. In its 2026-10-30 startup run, lightweight app counters reported about ten updates per second, with regular gaps around 100–118 ms while the policy remained active. The 90-update screenshot arrived about 11.5 seconds after window creation; the app completed and exited successfully. The existing normal baseline completed the startup-capture path in approximately two seconds. No Mesa overlay was enabled. The owning issue's private diagnostic evidence contains the immutable run manifest and log.

This run failed the required active responsiveness, so the implementation continued with the documented post-dispatch pacing seam. Later evidence below shows that the same approximately ten-update-per-second symptom also occurs with continuous active updates and coincident driver mapping failures. The original run therefore does **not** establish that the reactive timer policy caused the slowdown. Neither inspected Winit deadline code nor Bevy's gate specifies a 100 ms interval. Preserve the current implementation for comparison rather than switching mechanisms again on a confounded result.

## Work that must keep progressing

The application has several obligations that are not captured by “a key is currently held”:

- Camera following and appearance scaling interpolate toward a target. They need an explicit settled condition, with a small visual tolerance and final snap, rather than activity inferred indefinitely from floating-point inequality.
- Live harm stages and replay's current harm motion need updates until their intended motion/timer boundary; inspection and the asset dialog still govern pausing.
- Screenshot startup waits for 90 updates and completion waits for later updates. Pending capture must retain an active cadence, including F12 captures.
- The asset-folder dialog sends its result through a channel which is polled by the app. A finite heartbeat must remain available even when the user makes no further input.

These obligations come from the baseline [camera](../../src/tabletop_camera.rs), [Tony presentation](https://github.com/joeloverbeck/arkham-unfolded/blob/8c4e619e20f9a55dd2cbd3144ab21c26325d8af6/src/tony_tabletop.rs), [harm lifetime](https://github.com/joeloverbeck/arkham-unfolded/blob/8c4e619e20f9a55dd2cbd3144ab21c26325d8af6/src/tony_tabletop/harm_lifetime.rs) and [asset settings](https://github.com/joeloverbeck/arkham-unfolded/blob/8c4e619e20f9a55dd2cbd3144ab21c26325d8af6/src/tabletop/asset_settings.rs), not from a generic game-loop assumption. Scene and UI changes also need a brief settling interval so subsequent extraction/layout updates can complete.

Bevy processes internally completed asset loads through an app schedule and processes queued render pipelines through render updates. Neither the inspected asset nor renderer sources supplies a Winit wake hook for these completions. Do not sleep indefinitely merely because the scene currently looks unchanged. Keep startup/loading active until its relevant completion or failure is known, and retain the finite idle heartbeat as a conservative fallback. A failed/missing asset must not keep the application rendering at full rate forever. [Asset scheduling](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_asset/src/lib.rs), [Asset completion handling](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_asset/src/server/mod.rs), [Pipeline cache processing](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/render_resource/pipeline_cache.rs)

## Idle time must not become new animation time

Bevy's generic `Time` follows virtual time, whose default maximum single-frame delta is 250 ms. After a one-second idle interval, that is still a substantial first animation step. The existing action-before-timer ordering can otherwise charge time spent idle to a newly created harm stage, and a newly pressed camera key can produce a jump. Bound or reset the presentation delta on the idle-to-active transition; preserve ordinary elapsed-time progression during an already active animation. Do not globally replace real time with a fixed 1/60 second increment, which would distort slow-frame behavior. [Virtual time](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_time/src/virt.rs)

With pipelined rendering, `time_system` uses a timestamp received from the render thread, sent after rendering. Thus an idle gap can reach the app's `Time` one update after the input wake. Clamping only the update whose previous policy was idle is insufficient by itself. An app-owned monotonic presentation delta sampled at main-update start avoids this delayed-clock coupling; alternatively, the transition guard must cover the pending render-time samples. This is a source-derived failure case to test, not an observed native failure. [Time update system and channel](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_time/src/lib.rs), [Renderer time sender](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/lib.rs)

If visible timed motion remains active after focus loss, retain an appropriate active cadence until it settles. A one-second background update combined with the default delta clamp would stretch animation time; reducing rendering must not silently redefine the harm-stage lifetime.

## Limiter installation and evidence boundary

Bevy documents `RenderExtractApp`'s schedule as a frame-pacing seam after render dispatch and before the next input collection. Following the failed native probe, use a bounded `std::thread::sleep` there; sleeping in an ordinary `Update` system instead delays the current frame after its input was already collected. Measure elapsed time since the preceding pacing completion, sleep only the remaining part of 16.667 ms, and then establish a new completion instant. If a frame already exceeded the budget, do not add a full interval or run a catch-up burst. Ordinary sleep may overshoot, which is preferable to burning a CPU core for precision in this bounded application. Native cadence remains the oracle. [Pipelined renderer ordering](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/pipelined_rendering.rs)

`PipelinedRenderingPlugin::build` creates `RenderExtractApp`; `cleanup` moves the renderer to its thread but preserves that sub-app. A pacing plugin installed after `DefaultPlugins` can configure it in `finish`. The sub-app initially has `update_schedule = None`, so adding a system alone will not execute it: select an update schedule explicitly. Preserve its existing extraction function. The app calls extraction before the selected sub-app schedule, so the limiter executes after the renderer is dispatched and before control returns to Winit. [Plugin construction and cleanup](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/pipelined_rendering.rs), [Sub-app schedule and execution order](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_app/src/sub_app.rs)

The inspected upstream `bevy_framepace` 0.22.0 manifest targets Bevy 0.19, and its documented precision strategy uses `spin_sleep`. It is not a drop-in dependency for this pinned Bevy 0.20 application. Introducing a port or engine fork is not justified before testing the existing runner. [Upstream manifest](https://github.com/aevyrie/bevy_framepace/blob/main/Cargo.toml), [Upstream implementation overview](https://github.com/aevyrie/bevy_framepace#how-it-works)

Measure update cadence with lightweight counters, keeping it distinct from actual GPU presentation rate. Compare settled foreground, active camera and unfocused intervals at the same window size using the normal binary without the Mesa overlay that perturbed the earlier run. Pair GPU telemetry with actual camera, harm, replay, asset-completion and capture checks. Source review establishes the proposed mechanism; only that comparison can establish reduced work and preserved experience. A pacing improvement does not by itself resolve the mapping failures discussed below.

## Mapping failures confound the native comparison

Subsequent local evidence changes the interpretation of the first probe. The kernel's `dmaAllocMapping_GM107` allocation failure and `NV_ERR_NO_MEMORY` callback error coincide with the timer-only launch at 11:38:43 UTC, the unchanged published baseline at 11:45:47 UTC, and the later continuous-active candidate at 11:47:07 UTC. During the owner's later interaction with that candidate, counters again showed about ten updates per second with 107–121 ms gaps, and the owner reported severe lag. An earlier continuous-active startup at 11:41:56 UTC completed its 90-update capture about 1.8 seconds after window creation without a corresponding mapping error in the captured kernel interval. These launches are retained in the owning issue's private run manifests and logs; they do not form a clean causal comparison of pacing policies.

The later candidate executable is `7e402512d1263aebc0db0126313236c513bfc3ccaee0753cc0d275f9f3782c19`; the earlier successful startup candidate is `b01527ffda6edb4baafb310cb86a2506a83de92cc49f57a50a8f6291430a0748`. Their distinct identities must remain explicit. Per-process SM samples containing `-` do not establish zero GPU work: NVIDIA documents that unsupported metrics and collection errors also produce that value. Likewise, the reported reduction from approximately 1,571 MiB to 866 MiB of process GPU memory is an observation, not proof of an optimization or of which resource failed. [NVIDIA process-monitoring documentation](https://docs.nvidia.com/deploy/nvidia-smi/index.html#process-monitoring)

### What the error establishes

In NVIDIA's 615.78.08 source, the matching allocation message follows failure of `vaspaceAlloc`, which allocates a virtual-address range subject to size, alignment and range constraints. It is distinct from a direct allocation of physical framebuffer storage. The subsequent mapping-reuse assertion propagates failure from its mapping callback. Consequently, abundant free VRAM does not refute this error, while the error does not by itself identify an Arkham texture leak or defective hardware. [Virtual mapping allocator](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/nvidia/src/kernel/gpu/mem_mgr/arch/maxwell/virt_mem_allocator_gm107.c), [Mapping-reuse callback](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/nvidia/src/libraries/mapping_reuse/mapping_reuse.c)

The same release uses this mapping-reuse machinery for its BAR1 aperture. That path restricts normal mappings to the aperture and can retry some mappings in smaller chunks, depending on flags. NVIDIA defines BAR1 as the window through which the CPU or peer devices access framebuffer memory. This makes aperture/range pressure a credible hypothesis on a GPU reporting a 256 MiB BAR1, but the current log does not prove that BAR1 was full, that fragmentation caused this allocation, or that an application can repair the driver's retained state. Post-exit free-space readings cannot establish the failed launch's peak conditions. [BAR1 mapping implementation](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/nvidia/src/kernel/gpu/bus/arch/maxwell/kern_bus_gm107.c), [NVIDIA BAR1 definition](https://docs.nvidia.com/deploy/nvidia-smi/index.html#bar1-memory-usage)

NVIDIA staff acknowledged an earlier report of the same allocation-message family as internal bug 5762513. That discussion contains first-person Wayland/X11 and workload comparisons, but does not establish a verified fix for this exact 615.78.08/RTX 2080 Ti setup. A separate 615.78.08 report concerns `memoryMapperWorker`, a different warning; similarity is insufficient to equate its cause with this one. [NVIDIA tracking acknowledgement](https://forums.developer.nvidia.com/t/bug-report-wayland-only-dmaallocmapping-gm107-va-mapping-failures-does-not-reproduce-on-x11/353598/5), [Different 615.78.08 warning](https://forums.developer.nvidia.com/t/615-78-08-memorymapperworker-warning-numrefs-1-non-null-pmemorymapper-coincides-with-persistent-vulkan-rendering-stalls-on-rtx-4060-laptop/387130)

### Smallest app-level diagnostic

Before changing rendering features, test the same immutable executable with the process-only `WINIT_X11_SCALE_FACTOR=1` override. Winit documents this override for X11. Verify the resulting physical client dimensions: changing a 3200×2000 target to 1600×1000 quarters its pixel count. Bevy creates its main render textures from target dimensions and allocates an additional multisampled target when MSAA is enabled. Thus this probe reduces a concrete allocation demand while preserving the application and driver versions; it is not proof that these textures caused the mapping failure. It also changes window/UI size, so it is a diagnostic condition rather than an accepted permanent visual change. [Winit scaling](https://github.com/rust-windowing/winit/blob/v0.30.13/src/window.rs), [Bevy target allocation](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/view/mod.rs)

Measure cadence, allocation errors and actual responsiveness together. One successful reduced-size launch is insufficient when normal launches already alternate between good and bad. Do not simultaneously remove shadows, reduce MSAA and change the backend: that would conceal which demand mattered. A frame cap reduces repeated submissions; it does not necessarily reduce the size or number of allocations retained by the renderer.

The first size comparison did not isolate resolution as the cause. The unchanged `7e402512…` executable completed its 90-update capture at 1600×1000 in about 1.69 seconds, then at the original 3200×2000 in about 1.79 seconds. Its first measured intervals contained 53 updates in 1.011 seconds and 52 in 1.005 seconds, respectively; neither launch had a corresponding mapping error in the captured interval. Both are healthy startup observations, not sustained interaction acceptance or evidence that reducing resolution fixed the intermittent failure.

### Primary-buffer mappings and allocation hints

Disabling `MAPPABLE_PRIMARY_BUFFERS` again is unlikely to alter this application. Pinned Bevy already removes that feature from its automatic feature set for a discrete GPU; Arkham's baseline uses the default renderer settings, whose explicit features do not add it back. The observed adapter identifies itself as `DiscreteGpu`. This feature only relaxes which buffer usages may be combined; ordinary upload and readback buffers still need CPU mappings. Bevy's screenshot path, for example, uses `MAP_READ | COPY_DST`. [Bevy feature selection](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/renderer/mod.rs), [Bevy defaults](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/settings.rs), [Screenshot readback](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/view/window/screenshot.rs)

Cargo pins wgpu 30.0.1, upstream commit `40f4a34ebaf56f9a046231f54125ad046239d3f3`, and gpu-allocator 0.28.0. Wgpu's ordinary upload staging creates `MAP_WRITE | COPY_SRC` buffers. Its Vulkan backend classifies these as `CpuToGpu`; gpu-allocator first prefers host-visible, coherent, device-local memory when the buffer permits it, and maps an entire allocated block. Allocation failure can fall back to a host-visible coherent memory type. This provides a credible path for CPU mappings even with primary-buffer mapping disabled, but does not prove which Arkham allocation produced the NVIDIA message. [Wgpu staging](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-core/src/resource.rs), [Vulkan buffer placement](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/vulkan/device.rs), [Allocator mapping and fallback](https://github.com/Traverse-Research/gpu-allocator/blob/0.28.0/src/vulkan/mod.rs)

`WgpuSettings.memory_hints = MemoryHints::MemoryUsage` provided a more direct allocation-pressure probe than reducing visual quality. In this pinned backend, the default `Performance` hint selects device blocks of 128–256 MiB and host-visible blocks of 64–128 MiB; `MemoryUsage` selects 8–64 MiB and 4–32 MiB, respectively. Vulkan passes those sizes to gpu-allocator, which uses the host block range for host-visible memory, including memory that is also device-local. Smaller blocks reduce individual mapping demand and reserved slack; they do not cap total memory or split a resource larger than the block. This is a distinct candidate to compare repeatedly for errors, cadence and interaction, not a verified driver workaround. Extra allocation overhead is a possible tradeoff. [Wgpu allocation-size policy](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/lib.rs), [Vulkan allocator setup](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/vulkan/adapter.rs), [Host-visible block selection](https://github.com/Traverse-Research/gpu-allocator/blob/0.28.0/src/vulkan/mod.rs)

The smaller-pool candidate, executable SHA-256 `7b5560e237a4e975b8e0bcc466b6871aaa73aa2f008a4ff6e588b77a1a3715d3`, supplies important counterevidence. Its ordinary launch at 12:14:02 UTC produced the same mapping errors. After a startup interval of nine updates in 1.015 seconds with a 718.8 ms maximum gap, the next interval contained 60 updates in 1.004 seconds with a 17.0 ms maximum gap. It subsequently settled to the intended unfocused one-update-per-second cadence. Reported process GPU memory was 644 MiB versus an 804 MiB control. The memory observation supports evaluating allocation efficiency separately, but the run does not establish an error workaround or a sustained interaction fix. In particular, the mapping error is **not sufficient evidence of persistent ten-update-per-second behavior**.

No verified per-process NVIDIA setting or application-side reset for this failure was established by this bounded research. A full GPU reset is a host operation requiring other GPU clients, including graphics servers, to stop; it cannot be folded into an ordinary app launch. If controlled foreground comparisons remain unstable, a separately coordinated clean-session/reboot comparison is a possible diagnostic step, not a prerequisite inferred from the mapping message or a claim that reboot repairs its cause. [NVIDIA reset requirements](https://docs.nvidia.com/deploy/nvidia-smi/index.html#gpu-reset)

### Presentation waits, occlusion and screen sharing

Presentation can block without a slow application update system: Vulkan image acquisition waits when no presentable image is available, and FIFO queues presentation for display refresh. Bevy's pipelined extraction also waits for the preceding render world, so delayed rendering can propagate into measured main-update cadence. Those mechanisms make presentation delay plausible; they do not locate this run's 107–121 ms gaps. [Vulkan acquisition](https://docs.vulkan.org/refpages/latest/refpages/source/vkAcquireNextImageKHR.html), [FIFO semantics](https://docs.vulkan.org/refpages/latest/refpages/source/VkPresentModeKHR.html), [Bevy renderer handoff](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/pipelined_rendering.rs)

The bounded source inspection found no matching universal 100 ms fallback in the active Vulkan path:

## Cadence comparison on the owner's display

[#151](https://github.com/joeloverbeck/arkham-unfolded/issues/151) tested on 2026-11-11 whether the 60 Hz active cap caused the camera stutter Joel reported. The display is `DP-1`, 3840×2160 at 143.990 Hz, with scale 1.25 in a Wayland session. The application runs through Xwayland: Winit guessed an X11 scale factor of 2, and the adapter is an NVIDIA RTX 2080 Ti with driver 620.70.06 under Vulkan FIFO. This driver is newer than the 615.78.08 discussed above.

A decision-only build, commit `bd46afc8e73bf2a41430ca947e127512a1d41726` (executable SHA-256 `cbdd699cdebf1a7bf282fef4ea781bfe6d99523574ae596e62b6ae11594099a3`), let Joel switch the active limit with F9 within one launch. The modes were the 60 Hz baseline, a 72 Hz sleep cap (about two refreshes of the display) and no active cap. Joel used two launches, panning across the investigator tables, and reported that the second felt the same as the first. The second launch enabled the existing per-second update counter. Each row below covers only full seconds of continuous motion; the 60 Hz row excludes one 32.5 ms gap during the startup graphics check. Window size, focus and screen sharing were not recorded for either launch.

| Active mode | Seconds | Updates per second | Longest gap in a second | Joel's judgement |
| --- | --- | --- | --- | --- |
| 60 Hz cap | 21 | 59–61, mean 60.0 | 16.8–17.1 ms | "Very stuttery": the camera "hitches and then advances to catch up", "more or less constantly" |
| 72 Hz cap | 15 | 72, mean 72.0 | 14.1–14.2 ms | "Slightly less stuttery/hitchy", but "it wasn't fixed" |
| No active cap | 23 | 121–145, mean 136.3; 11 seconds below 140 | 8.5–17.0 ms | "The smoothest", but it "didn't fix the camera-hitch effect fully" |

Both caps held their target rates, with gaps no more than about 0.4 ms above the cap, which is consistent with sleep overshoot. So the stutter under a cap does not come from slow application updates. A likely explanation is that a sleep cap is not locked to the display's refreshes:
- At 60 Hz on a 144 Hz display, consecutive frames stay on screen for two or three refreshes, alternately.
- At 72 Hz, small variations in render completion can push frames across a refresh boundary.

Without the cap, presentation paced the frames, but the application did not sustain one frame per refresh. Seconds with 121–137 updates and gaps up to 17 ms show that some updates took longer than the 6.9 ms refresh interval. Missed refreshes are a plausible source of the remaining hitch; that has not been established.

These counters time application updates; they are not presentation timestamps. The refresh-hold explanation is therefore inferred from the measured rates and Joel's description, not observed directly. The comparison covers one desktop, one unrecorded window state and one scene region. It does not establish behaviour on another display rate, nor while the window is hidden. In that case, presentation pacing should still bound active frames through Xwayland's 17 ms copy timer and 1000 ms flip fallback (table above), but this was not observed. The counters show that update overruns exist, not their source.

Decision: Joel judged the no-active-cap mode the smoothest but not a full fix. Before the logged launch, he accepted adopting it as a partial result if that launch confirmed each mode's rate. Both caps held their rates. With no cap, the mean was 136.3 updates per second, short of one frame per refresh; that shortfall is the overrun described above. Active frames are no longer capped, and FIFO presentation paces them. The 60 Hz limiter still applies while the table stays settled. Idle throttling, the upload-memory patch and the rendering-health guard are unchanged.

This knowingly departs from the issue's "one-line revert": the limiter needs the settled state from the main app, so the change shares a flag with the render-extract sub-app. The remaining hitch needs its own diagnosis decision; [#151](https://github.com/joeloverbeck/arkham-unfolded/issues/151) holds the current status.

## Decorative rate comparison

[#188](https://github.com/joeloverbeck/arkham-unfolded/issues/188) tested, on 2026-11-12, whether slow looping decorations could be drawn below the display rate. Since the change above, any request held the display rate. While a choice is offered, the window is focused and Reduced motion is off, the availability cue asks for a frame on every update. So the table drew at 144 Hz through most of play, even with the camera still. The display and adapter were those described above. At its start the log gave the window as 6010×3318 physical pixels; whether it stayed maximised was not reported.

A decision-only build, commit `79f1092` (executable SHA-256 `38a7709ccfcbceeedc56437aae5a83c9a24f72e9c639df0d466f0d214541cf1a`), added a third pacing state. When only the cue's breathing, the reveal control's pouch bob and the encounter reading's tendrils ask for frames, Winit waits a fixed interval that window input ends at once. Keys selected 60/s, 30/s, or the display rate as before. The build recorded the update counter and one `nvidia-smi` reading per second. The launch stood at a pending token reveal, with the cue on three components. Its route asked Joel to hold each setting for 75 s with his hands off the mouse and keyboard; every measured hold lasted at least 60 s, and only stretches in which the window was focused were measured. The [evidence record](https://github.com/joeloverbeck/arkham-unfolded/issues/188#issuecomment-6828779965) holds the full readings and limits.

| Decorative rate | Mean power W | Updates per second | Joel's judgement |
| --- | --- | --- | --- |
| Display rate (before) | 198.9 | 143.7 | Reference |
| 60/s | 78.0 | 60.2 | "At 60/s and up, I didn't notice any particular issue" |
| 30/s | 69.6 | 30.3 | The breathing "didn't look as smooth"; "it felt like it didn't progress smoothly from opaque to translucid and back" |

Joel said the pouch bob "did seem to look the same", without naming a rate. Between holds, while the window was briefly unfocused, the table settled and the card drew 30–45 W. Joel did not hear the fans run high.

Decision: under the accepted rule, the lowest capped rate that Joel judged unchanged and that drew at least 40 W less than display rate is 60/s. The cue's breathing and the pouch bob are drawn at 60/s when nothing else asks for frames. Camera, card and map motion, presentations, checks, captures, the hover fade and any input keep the display rate. An update that input wakes after a decorative wait moves at most one 60/s step. The encounter reading's tendrils were not judged, because no reading came up in the launch, so they keep the display rate. An open reading does not count as presenting. During a reading, the tendrils hold that rate while the window is focused, Reduced motion is off and rendering health allows play. The rendering-health hang watchdog stays armed while decorative. The progress check after admission still counts only display-rate frames.

The comparison covers one scene, view and window state on one display. It does not establish judgement of the tendrils at a capped rate, nor the fans' long-run behaviour.
