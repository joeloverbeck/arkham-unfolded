# NVIDIA mapping failures and startup health

Research on 2026-10-31 supports the owner's investigation of unplayable intermittent lag while testing [#55](https://github.com/joeloverbeck/arkham-unfolded/issues/55). The investigation baseline is `8a08cc9ddac849ca39380fb5df2d49d62129da89`, with Bevy 0.20.0 and wgpu 30.0.1. This note supplements [the earlier frame-pacing investigation](tabletop-frame-pacing.md), retaining its counterevidence. The final section describes the subsequently approved application protection; no verified driver fix is claimed.

## What the NVIDIA error means

The installed-driver version reported during this investigation is 615.78.08. In that exact public source, `dmaAllocMapping_GM107` emits the observed allocation message after `vaspaceAlloc` cannot obtain a virtual-address range satisfying size, alignment and range constraints. This function handles several address-space kinds, including BAR1. Its name alone does not identify the specific caller or aperture. The assertion at `mapping_reuse.c:273` propagates failure from a new-mapping callback. Neither message directly says that physical video RAM is full. [NVIDIA allocator, lines 412–419 and 1018–1024](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/nvidia/src/kernel/gpu/mem_mgr/arch/maxwell/virt_mem_allocator_gm107.c#L1018), [mapping callback](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/nvidia/src/libraries/mapping_reuse/mapping_reuse.c#L273)

NVIDIA describes BAR1 as an aperture mapping device memory for CPU or peer-device access. Its capacity and current use are distinct from framebuffer memory use. Therefore abundant free VRAM is compatible with a failed mapping; a single BAR1 occupancy reading also cannot identify fragmentation, a transient peak, or the failed allocation's constraints. The latter are inferences from the allocator's requirements, not diagnoses of this host. [BAR1 definition](https://docs.nvidia.com/deploy/nvidia-smi/index.html#bar1-memory-usage), [allocation constraints](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/615.78.08/src/nvidia/src/kernel/gpu/mem_mgr/arch/maxwell/virt_mem_allocator_gm107.c#L1018)

The previous local investigation already recorded the same error followed by recovery to 60 updates in 1.004 seconds with a 17.0 ms maximum gap. It also recorded healthy launches at both 1600×1000 and 3200×2000. Consequently, neither this kernel message nor large window size is sufficient to classify a launch as persistently unplayable. A reduced-size run and a smaller allocation-pool run are historical probes, not established solutions. [Retained local observations](tabletop-frame-pacing.md#mapping-failures-confound-the-native-comparison)

## What the application can observe

wgpu distinguishes GPU API errors from surface acquisition outcomes. GPU errors include out-of-memory, validation and internal errors; they may arrive synchronously or asynchronously and normally panic unless captured by an error scope or uncaptured-error handler. Device loss has a separate callback. These are suitable inputs for an explicit failure path, but a kernel mapping warning is not guaranteed to arrive as an application-visible out-of-memory error. [wgpu error contract](https://docs.rs/wgpu/30.0.1/wgpu/enum.Error.html), [device callbacks](https://docs.rs/wgpu/30.0.1/wgpu/struct.Device.html#method.set_device_lost_callback)

Pinned Bevy already installs those handlers. Its `DeviceErrorHandler` records device loss and uncaptured errors; the default `RenderErrorHandler` logs the failure, emits `AppExit::error()` and stops rendering. Thus the present engine does not intentionally ignore a reported GPU out-of-memory error and continue playing. At the investigation baseline, a separate local reporting defect existed: the native experiment run functions discarded the `AppExit` returned by `app.run()` and returned `Ok(())`. The protection below propagates that exit status so a genuine renderer exit is visible to the caller; this does not explain or repair a still-running slow frame loop. [Pinned Bevy error handling](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/error_handler.rs#L65), [party launch wrapper](../../src/party_tabletop.rs)

In wgpu 30.0.1, acquisition produces `CurrentSurfaceTexture`, with success, suboptimal, timeout, occluded, outdated, lost and validation outcomes. Timeout and occlusion ordinarily call for skipping a frame; outdated configuration calls for reconfiguration; device loss requires more extensive recreation than surface loss. Treating every skipped frame as a permanent failure would reject legitimate transitions. [Surface acquisition outcomes](https://docs.rs/wgpu/30.0.1/wgpu/enum.CurrentSurfaceTexture.html)

Bevy 0.20's `prepare_windows` accepts a successful or suboptimal texture, retries after an outdated configuration, skips occlusion, and logs other acquisition failures. Some Linux timeouts receive a trace-level driver-quirk treatment. The code does not establish an application-specific sustained-performance verdict. Its presentation method schedules presentation rather than proving that a frame has reached the display. [Pinned Bevy window renderer](https://github.com/bevyengine/bevy/blob/v0.20.0/crates/bevy_render/src/view/window/mod.rs#L259)

Adapter/device creation and asset loading therefore cannot certify playable performance. An initialization check can catch an explicit allocation failure; it cannot prove that subsequent asynchronous rendering, compositor presentation or later allocations will remain healthy. This is an inference from those API boundaries, supported by the local healthy-after-error counterexample.

## Recommended decision path

First measure the current symptom using the actual affected executable and view. Distinguish main-thread work, renderer handoff, GPU completion and surface presentation. Keep window size, foreground visibility, sharing state, loaded scene and active/idle policy explicit. An app-update counter is useful but is not a display-frame counter; the intentional one-second background heartbeat must not become a false failure. The earlier note explains the relevant Bevy/Vulkan handoffs. [Existing measurement limits](tabletop-frame-pacing.md#presentation-waits-occlusion-and-screen-sharing)

For a bounded next comparison, change only one condition: close the accelerated browser after preserving its user work, then relaunch the identical application at the identical size and measure again. Only the owner can authorize disrupting unrelated desktop applications. If the symptom remains, browser pressure loses priority for this case; if it clears repeatedly, that supports a local workaround but still does not identify the driver's internal defect. A normal YouTube video in another window neither verifies nor refutes Arkham's separate rendering/presentation path.

The initial recommendation was a shared startup health phase before accepting gameplay, followed by continued failure monitoring. The owner subsequently approved this direction; the implementation and evidence limits are recorded below:

- Preserve Bevy's existing fatal handling for explicit GPU out-of-memory/internal failure and device loss, propagate its unsuccessful exit status, and make the explanation readable while preserving the existing record. A custom callback must retain that failure path; merely suppressing errors would conceal them.
- Load the real scene, allow bounded shader/asset warmup, and force a known active cadence while collecting the health sample. Admit gameplay only after the relevant render work progresses within the selected responsiveness budget. Timeouts must be bounded so a stalled renderer cannot leave an indefinite loading screen.
- Explain an observed sustained stall as a rendering-health failure unless the cause is established. Include the adapter, driver, backend, window size, interval and error class in local diagnostics. Provide an ordinary exit/retry path; no automatic driver reset or browser termination.
- Exclude minimized/occluded windows and expected loading transitions from a normal-play performance verdict. Monitor after startup as well, because later allocation and presentation failures remain possible.
- Validate the gate against both a captured bad run and the healthy-after-warning case. Prove that refusal does not create, overwrite, replay or advance a player's session. Use visible controls to test the recovery path when rendering is healthy again.

Numeric thresholds should be selected from measured good/bad foreground samples and the required interaction budget. A GPU-memory percentage, a matching journal line, or a fixed sleep is not a substitute for this evidence. An app can refuse entry into gameplay after a failed startup check; it cannot guarantee that the graphics driver will never fail after that check.

NVIDIA's documented reset operation requires competing GPU clients, including graphics servers, to stop. It is therefore unsuitable as hidden app-launch recovery. Persistent tooling should prefer NVML's stable interface over parsing `nvidia-smi` text, but an NVML dependency is not needed merely to implement app-owned error and progress checks. [Reset requirements and monitoring-interface stability](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

## Launch environment is a comparison variable

The [native launcher](../../tools/src/native.rs) gives every run fresh `XDG_CACHE_HOME`, `XDG_CONFIG_HOME` and `XDG_DATA_HOME` directories and a staged executable/current directory; other environment variables are inherited. This differs from the owner's ordinary launch. NVIDIA's exact 615.78.08 README documents `__GL_SHADER_DISK_CACHE_PATH` as the explicit shader-cache path override, otherwise using `XDG_CACHE_HOME/nvidia/GLCache` or the home-directory fallback, with legacy cache-location reuse. It also documents `__GL_SHADER_DISK_CACHE` and `__GL_SHADER_DISK_CACHE_SIZE`. That chapter explicitly concerns OpenGL, so its text alone does not establish Vulkan behavior. [Versioned NVIDIA cache settings](https://download.nvidia.com/XFree86/Linux-x86_64/615.78.08/README/openglenvvariables.html)

Local evidence closes that narrower gap for the observed Vulkan launches: all three owned diagnostic directories (`run-1-normal`, `run-2-normal`, `run-3-normal-tail`) contain NVIDIA `.bin`/`.toc` cache files beneath their isolated `cache/nvidia/GLCache/` paths. Their logs identify the RTX 2080 Ti, driver 615.78.08 and Vulkan backend. Thus cache location really differed; this does not prove that cache state caused or cured the lag. The relevant evidence is retained with the run manifests under the investigation's local evidence directory. Cache warmth, isolated configuration, cwd, logging and process startup history must remain explicit differences when comparing these runs with an ordinary launch; no user cache was removed or altered for this comparison.

Pinned Bevy reads `WGPU_ADAPTER_NAME` and `WGPU_FORCE_FALLBACK_ADAPTER`; its defaults also obtain backend and power preference from wgpu's `WGPU_BACKEND` and `WGPU_POWER_PREF`. The actual adapter log remains the check on which choice occurred. [Bevy selection](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/renderer/mod.rs#L261), [Bevy defaults](https://github.com/bevyengine/bevy/blob/b3bdd75becaffe9a16677cf5bae5bd6d198f052b/crates/bevy_render/src/settings.rs#L84), [wgpu backend parsing](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-types/src/backend.rs#L153), [wgpu power preference parsing](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-types/src/adapter.rs#L89)

The Vulkan loader separately honors `VK_DRIVER_FILES` (preferred over deprecated `VK_ICD_FILENAMES`), `VK_ADD_DRIVER_FILES`, and driver select/disable filters. Linux driver discovery also searches XDG configuration/data paths. Therefore changing those directories can alter locally installed driver discovery, though no such change is established here. A matched diagnostic should record these specific settings without dumping unrelated environment secrets, and compare actual adapter/driver/backend identities. [Khronos loader discovery and overrides](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDriverInterface.md#overriding-the-default-driver-discovery)

## Research disposition

The initial source research and five explicitly approved diagnostic launches produced no application-code or host-setting change. The original save and source archive were preserved; all diagnostic processes ended. No permanent lag fix or #55 gameplay acceptance is claimed. The ordinary launch method remains unproved as the cause.

The owner then approved the bounded startup/ongoing rendering-health protection, including correct propagation of fatal renderer exit status. ## Recurrence and approved protection

After the first comparison, the owner reported one healthy ordinary Cargo launch followed by three consecutive lagging launches with the same command. Kernel mapping errors occurred at 10:24:55, 10:25:06 and 10:25:34 UTC. The processes had already ended when inspection resumed. The selected journals showed no matching GPU reset, Xid, suspend/resume, system out-of-memory event or compositor restart. Current memory use cannot reconstruct the failed allocation. One NVIDIA cache pair changed during the failures, but the same pair also grew during a healthy copied-cache run; this does not establish corruption.

Two further 30-second baselines used the unchanged executable, copied saves, the ordinary cache/configuration and no screenshot request. Direct execution started with 41 updates/s and then approximately 60 updates/s. The exact `cargo run` form started with 38 updates/s and then transitioned to the expected background cadence. Neither interval produced a matching mapping error. Both ended at their intentional deadline. These comparisons remove the claim that an isolated cache or screenshot request was necessary for recovery; they do not explain the intermittent state transition. Evidence is retained under `~/.cache/agent-tmp/arkham-gpu-guard/`.

The shared [rendering-health module](../../src/tabletop_health.rs) now governs admission in all three native experiments. It leaves the real scene visible beneath a “Checking graphics…” overlay and discards authoritative input until admission, including input queued on the admission frame. Camera navigation and dismissal remain available. Explicit renderer failures preserve Bevy's existing handler and now reach a nonzero command result.

The selected policy allows two seconds of scene/asset/pipeline warmup, followed by three consecutive one-second samples at at least 30 main updates and 30 completed GPU submissions per second. The GPU counter acknowledges acquired-surface work after submission; callbacks from older sampling generations cannot inflate a new sample. This is completed GPU work, not a measured display presentation timestamp. The 30/s floor is a conservative implementation choice below the observed healthy approximately 60/s active cadence, selected before the later captured bad run; it is not a universally calibrated playability threshold.

Startup has a total 30-second visible foreground budget, including loading. Background, occluded and intentional idle intervals do not count as slow gameplay. The health phase requests active redraw while visible and focused. After admission, sustained poor progress across at least three eligible seconds stops gameplay and exits unsuccessfully. A separate cancellable watchdog exits if an already-active foreground main loop stops updating for 15 seconds. It relies on last-observed focus/visibility during a hang and starts after renderer creation; it cannot bound device initialization before installation or guarantee a visible error if rendering itself is blocked. Normal failures log an explanation; a restart is the retry path.

Policy and production-plugin tests exercise slow/missing GPU completion, callback expiry, recovery before the deadline, excluded intervals, fatal exit propagation and watchdog cancellation. Adapter tests exercise pending-decision/save preservation, queued input, replay/restart blocking and delayed screenshot capture. These prove application mechanics, not the NVIDIA root cause or physical input responsiveness. Review additionally found and fixed watchdog arming on an idle-to-active transition: the watchdog now follows the current frame's final cadence before render extraction can block. The production pacing/health regression failed before this correction and passed afterward. No driver settings, browser settings, cache cleanup or player-record migration is part of the protection.

## Follow-up on the launch-method difference

The owner's renewed request selected three further comparisons; the owner then explicitly approved two additional 45-second comparisons. All five used the final `698530…ed77` executable bytes. Read-only inspection found no per-user Vulkan manifests or party configuration file in the ordinary configuration/data locations. The explicit artwork path bypasses defaults. Selected graphics/layer overrides were absent, and the ELF has no RPATH/RUNPATH. These facts remove several concrete explanations without proving that launch context is irrelevant.

| Comparison | Result |
| --- | --- |
| Reuse the previously healthy staged executable, cwd, XDG directories, artwork and copied save; omit screenshot/quit arguments | Approximately 11 main updates / 10 GPU completions per second; mapping error at 11:06:13 UTC; app refused play, exit 1 |
| Same reused setup; restore screenshot/quit arguments | Again approximately 11/10; mapping error at 11:07:35; app refused play, exit 1 |
| Fresh native-helper staging with the same executable bytes, no screenshot option | Three healthy approximately 59.8/58.8 samples; admitted play; intentional 45-second supervisor timeout, exit 124 |
| Reuse the previously failing setup, start the bounded app in the shell background, hash its executable concurrently, then wait | Healthy approximately 60/59; admitted play; hashing ran for 0.97 seconds during startup; intentional timeout, exit 124 |
| Same background-supervised setup, remove the hashing step | Healthy approximately 60/59; admitted play; intentional timeout, exit 124 |

The matched screenshot removal/restoration did not toggle recovery, and the fresh helper admitted play without screenshots. Code inspection confirms that screenshot readback is deferred until after admission. Before admission the screenshot option only requests redraw, which the health check already requests in the foreground; it can change background cadence. Screenshot capture is therefore not a demonstrated remedy.

The helper hashes the running executable during startup after staging it. The last pair tested a similar concurrent read using `sha256sum`. Both conditions were healthy, so a concurrent hash was not necessary in that pair. The pair also used background shell supervision, while the preceding reused failures ran as foreground commands. Fresh staging, standard-input/process supervision, startup timing and driver state carried across launches remain unseparated. A persistent effect from an earlier read is not excluded. No deterministic launch fix or underlying NVIDIA mechanism is established.

Selected graphics environment and mapped-library evidence were retained for the healthy fresh-helper and final no-hash runs. Later attempts to read process details after other runs had exited failed and supply no environment evidence. The portable result is a repeatable-looking association between launch conditions and recovery, plus specific eliminated hypotheses; it is not permission to hide a hash, cache reset or broad host change in normal startup. The next narrow comparison would keep executable/argv/environment/cwd and prelaunch reads fixed while explicitly matching standard input and process supervision between foreground and background launches.
